## Makefile
Automatic variable
- $@ target name
- $? all prerequisites newer than target
- $ ^ output all prerequisites
- $< output the first prerequisite

Implicit rules
- Compile a C program `$(CC) -c $(CPPFLAGS) $(CFLAGS) $^ -o $@`
- Compile a C++ program `$(CXX) -c $(CPPFLAGS) $(CXXFLAGS) $^ -o $@`
- Linking a single object file `$(CC) $(LDFLAGS) $^ $(LOADLIBES) $(LDLIBS) -o $@`

Implicit vars
- `CC` Program to compile C progs default cc
- `CXX` Program to compile C++ progs default g++
- `CFLAGS` Extra flags to give to the C compiler
- `CXXFLAGS` Extra flags to give to the C++ compiler
- `CPPFLAGS` Extra flags to give to the C preprocessor
- `LDFLAGS` Extra flags to give to compilers supposed to invoke the linker

## Libft Problems

### Void pointer dereference / memset

**Q:** Casting `void *` to `unsigned char *`, then dereferencing to implement `memset`, gives `error: dereferencing 'void *' pointer` and `invalid use of void expression` even with `-Werror`.

**A:** `ptr[i]` is `*(ptr + i)`. Pointer arithmetic needs a complete type — `void` is incomplete, so `ptr + i` is ill-formed (GCC's `void *` arithmetic is a non-standard extension, rejected under `-Werror`/`-pedantic`). Even if allowed, `*(ptr + i)` yields a `void` expression, which is not a modifiable lvalue — hence "invalid use of void expression". The cast doesn't help if the *result* is stored back into a `void *` variable: a variable's type is fixed at declaration; the assignment implicitly converts the cast result right back to `void *`. Fix by indexing through a variable (or inline expression) whose declared type is `unsigned char *`.

### Modifying original memory without returning (bzero)

**Q:** Implementing `bzero` (returns `void`) without return — does editing through a local `unsigned char *` actually change the original memory block?

**A:** Yes. A `void *` parameter carries the original block's address; `unsigned char *p = (unsigned char *)ptr;` copies that address, so `p` and `ptr` point to the same memory. `p[i] = 0;` writes through that address into the block itself — independent of which pointer variable is used. `bzero`'s effect is a side effect (mutating memory), not a return value, so no return is needed. Only fails if you make `p` point elsewhere or never write through it.

### strchr

**Q:** This `ft_strchr` "apparently cannot be done this way":

```c
char *ft_strchr(const char *s, int c)
{
    int i = 0;
    while (s[i])
    {
        if (c == s[i])
            return (s + i);
        ++i;
    }
    if (c == s[i])
        return (s + i);
    return (NULL);
}
```

### strchr with out-of-range int c

**Q:** What if `c` isn't in ASCII range?

**A:** `c` is converted to `unsigned char` internally; only the low byte is matched. No failure — just a truncation. Returns `NULL` if not found.

### strncmp with negative char

**Q:** Why does the test stuff `SCHAR_MIN` / `-42` into the string?

**A:** To check `ft_strncmp` treats bytes as `unsigned char` when comparing, matching libc. The test only compares the **sign** of the return value (`sign()` lambda), not the exact number, since the standard only guarantees the sign.

### strlcat return value when size = 0

**Q:** `dest = "B"` (len 1), `size = 0` — why is return `strlen(src)` (=9), not `1 + 9`?

**A:** BSD `strlcat` computes `dlen` by scanning `dst` **no further than `size`**. With `size = 0`, `dlen` is treated as `0`, so return is `0 + strlen(src) = 9`. Nothing is written to `dst`.

### size_t parameter receives a negative value

**Q:** What happens when `strnstr` gets a negative `size_t`?

**A:** Implicit conversion to a huge unsigned value (`SIZE_MAX` on 64-bit). The search limit effectively disappears → reads out of bounds → undefined behavior. Never pass negative values to `size_t`.

**Q:** How do I get the big value from `size_t`?

**A:** You don't need to — the conversion is automatic. To write it explicitly: `SIZE_MAX` (from `<stdint.h>`) or `(size_t)-1`. And **don't** cast `size_t` down to `unsigned int`; it truncates on 64-bit.

### strnstr inner-loop ++i

**Q:** Do I need the extra `++i` on mismatch inside the inner loop?

**A:** No. The outer loop already does `++i` once per iteration. Adding another inside skips `i+1` as a candidate start (e.g. `big="aab"`, `little="ab"` → misses the match at index 1). Just `break` on mismatch and let the outer loop advance.

## calloc overflow handling

**Q:** What's wrong with returning `malloc(1)` on overflow?

**A:** `calloc` must return **`NULL`** when `n * size` overflows — returning `malloc(1)` makes the caller think it got `n * size` usable bytes. Order matters too: check `n == 0 || size == 0` **before** dividing (`SIZE_MAX / size`) to avoid division by zero. Precompute `total = n * size` instead of recomputing it each loop iteration.
